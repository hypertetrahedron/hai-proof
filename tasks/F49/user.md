I maintain a plugin with options like "a number of lines, or the word auto". Here is the design I want for `Parser.addini(..., type=...)`:

- The existing string tags (`"string"`, `"int"`, `"bool"`, and so on) keep working exactly as before. In addition `type=` takes the plain Python types `str`, `bool`, `int` and `float` as aliases of the tags `"string"`, `"bool"`, `"int"` and `"float"`. `type=int` on a TOML integer gives that integer.
- It also takes a union of those types, such as `int | str`, and a `Literal` of strings such as `Literal["auto", "long"]`. A `Literal` can be a member of a union too, for example `int | Literal["auto"]`.
- Anything else is a mistake and `addini` raises `ValueError` straight away: an unknown tag such as `"integer"`, a type like `dict`, a union containing an unsupported member like `int | dict`, and a `Literal` with a non-string choice such as `Literal["auto", 1]` (also inside a union, `str | Literal[1]`). The message should start with "invalid type for ini option 'name'"; for the non-string choice it should say the Literal choices must be strings.
- A union or `Literal` type has no sensible implicit default, so if you register one without passing `default=`, `addini` raises `ValueError`. The message should say it is a "union type" or a "Literal type" which has no implicit default and that an explicit default is needed. An explicit `default=None` is fine, and when the option is not set `getini` returns the default as given.
- Reading a union value: in a TOML config (`[tool.pytest]`) the value keeps its native TOML type, and the first member that accepts that type wins. With `int | str`, TOML `7` gives the int `7` and TOML `"7"` gives the string `"7"`. In string-based sources (an `.ini` file, `[tool.pytest.ini_options]`, which stringifies, and `-o name=value`), the string is coerced to the first member that accepts it, in order, so with `int | str` the text `7` gives the int `7`, and with `int | Literal["auto"]` the text `auto` gives `"auto"` and `3` gives `3`.
- If no member accepts the value, `getini` raises `TypeError`, not `ValueError`. For example a TOML list `[1, 2]` for `int | str`: the message says "config option 'ini_param' expects one of int | string". For `int | Literal["auto"]` with TOML `"3"` it says "expects one of int | 'auto', got str: '3'".
- A `Literal` alone is a plain string checked against the choices, with no coercion, in both TOML and ini modes. A TOML string that is not one of the choices raises `ValueError`, with the message "config option 'ini_param' expects one of 'auto' | 'long', got 'short'". A TOML value that is not a string at all (say `5`) raises `TypeError`: "config option 'ini_param' expects a string, got int: 5".
- If the option is unset, `getini` returns the `Literal` option's default (for example "auto").
- Errors raised by `getini` name the config file path and the option name, as the current ones do.
- `pytest --help` should display union and `Literal` types readably, with members joined by " | ", for example `ini_union (int | string)`, `ini_literal ('auto' | 'long')`.
