# Authoring hai-proof tasks

A task is one coding job that both arms of a run attempt. The published suite uses **public Python
repos pinned by commit SHA** (DESIGN §4.1), so anyone can rebuild and rerun it.

## Layout

```
tasks/<ID>/
  task.toml          # metadata, source pin, install, acceptance tests
  prompt.md          # what a developer would type — never mentions hidden tests
  inject.patch       # bug tasks only: author-written bug, applied on top of `base`
  hidden_tests/      # mirrors repo paths; copied onto the repo only AFTER the agent exits
  reference.patch    # the fix / feature, applied on top of the start state
  repo/              # generated by `hai-proof build-task` (gitignored; never edit by hand)
  source.lock.json   # generated
```

## task.toml

```toml
id = "B1"
kind = "bug"              # bug | feature
level = 1                 # 1..3 (see difficulty below)
origin = "injected"       # injected (author-written bug) | authored (author-written feature) | upstream-fix
timeout_s = 1200
budget_usd = 3.0          # L1 3.0 · L2 5.0 · L3 8.0
max_turns = 40            # L1 40 · L2 60 · L3 80
install = "uv pip install --python /opt/venv/bin/python -e . pytest"   # runs in /work at image build
acceptance = ["tests/hai_proof/test_b1.py"]
# regression = "python -m pytest -q -p no:cacheprovider tests"         # optional override

[source]
kind = "git"
url  = "https://github.com/<org>/<project>.git"
base = "<full 40-hex commit SHA>"
```

## Rules

- **Pin a full SHA** of a released tag (record the tag in a comment). Permissive license only
  (BSD/MIT/Apache). The repo's own test suite must run in **under ~60 s** and need no services
  (no network, database, GPU).
- **Hidden tests** live under `hidden_tests/tests/hai_proof/test_<id>.py` (lower-case id) so they never
  collide with upstream files. They must FAIL at the start state and PASS with `reference.patch`.
  Test behaviour through the public API, not the exact implementation, so any correct fix passes.
- **Bug tasks** (`inject.patch`): a small, plausible mistake — the kind a real commit could introduce.
  `reference.patch` is the exact reverse of `inject.patch`.
  - L1: existing tests may catch it; the prompt includes the failing call and traceback.
  - L2/L3: the pre-existing suite must still PASS with the bug injected (pick an untested path), so
    the agent has to diagnose from the reported symptom.
- **Feature tasks**: no `inject.patch`; `reference.patch` implements the feature following the
  project's existing patterns (docstrings, type hints, changelog entry if the project keeps one is
  optional — hidden tests must not depend on docs).
- **prompt.md** reads like a real issue or a colleague's request. Never mention hidden tests, the
  `tests/hai_proof/` path, or hai-proof. Don't tell the agent how to fix it beyond what a reporter
  would know. Don't say "run the tests".
- `diff_categories` overrides are rarely needed; leave them out unless the repo has unusual layout.

## Difficulty

| Level | Bug | Feature |
|---|---|---|
| 1 | Wrong result in one function; prompt has failing input + traceback | Add a parameter/flag to an existing function or command |
| 2 | User-visible symptom; cause one or two modules away from where it shows | New capability touching 2–3 layers, following existing patterns |
| 3 | Cross-cutting or state-dependent defect with a misleading symptom | Feature that needs a small refactor first |

## Build and validate

```sh
uv run hai-proof build-task tasks/<ID>          # clone @ base, strip .git, apply inject.patch
uv run hai-proof validate-task --tasks <ID>     # on the execution host; no API spend
```

`validate-task` must report `[ok]`: acceptance fails at the start state; acceptance and the
pre-existing suite pass with `reference.patch` applied. It warns if grading takes over 60 s.

Final calibration needs real agent runs (DESIGN §4): a 3-run single-arm pilot of the plain arm must
solve each task at least 2 of 3 times, and levels must order by median wall-clock and tokens within each
track (bugs, features).

### Calibration notes (claude-sonnet-5-5, Claude Code 2.1.292, 2026-10-07)

| Task | Median wall | Median tokens | Turns |
|---|---|---|---|
| B1 · L1 | 11 s | 82k | 5 |
| B2 · L2 | 38 s | 125k | 7 |
| B3 · L3 | 48 s | 159k | 7 |
| F1 · L1 | 43 s | 118k | 7 |
| F2 · L2 | 62 s | 237k | 10 |
| F3 · L3 | 161 s | 642k | 16 |

Lessons from tuning:
- This model localises a bug in a small library within a few tool calls however misleading the symptom;
  one-line defects stay under a minute. B2 and B3 are therefore *regression reports* with three
  independent related defects each, which scales time more reliably than a single subtle bug.
- Features scale with scope: each additional specified behaviour adds turns. F3 went from 29 s to
  161 s by spanning Table, Panel and Tree with a shared renderable.
- Earlier absolute targets (L2 2–5 min, L3 5–15 min) were not reachable with these repos; the suite is
  calibrated on ordering. Harder L3 work likely needs a larger repo or a longer feature.
