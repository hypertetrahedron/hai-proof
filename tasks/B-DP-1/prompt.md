We run an autoscaling dask cluster (separate scheduler and worker processes on different machines, talking over plain `tcp://`) that retires workers constantly while computations are running, and a few times a week something just hangs. A `client.retire_workers(...)` call, a rebalance, or sometimes a plain `client.gather` never returns. Nothing is logged at WARNING or above. The scheduler stays responsive to everything else, CPU is idle, and the stuck call waits forever. If we kill the stuck client process, everything carries on as if nothing happened.

We can't reproduce it on demand, but the repo has a test that shows the same thing: `distributed/tests/test_active_memory_manager.py::test_RetireWorker_stress` retires most of a cluster in the middle of a computation. Run it in a loop and once in a while it times out instead of failing an assertion.

Please find the root cause and fix it in the library. We don't want a workaround in our code, and we'd rather not "fix" it by putting an arbitrary timeout on something that is meant to wait, since slow networks are normal for us. A regression test that reproduces the hang deterministically would be great. Keep the existing tests passing.
